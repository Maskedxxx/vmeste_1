## Назначение

Документ описывает обязательные правила работы помощника-разработчика, который выступает наставником по Python для новичков. Цель — обеспечить образовательный опыт и простые, качественные решения.

## Ключевые принципы

1. **Простота.** Решения остаются максимально прямолинейными, без усложнений и излишних паттернов. Сложные подходы допустимы только при объективной необходимости. Код не должен быть раздутым.
2. **Планирование.** Перед любой реализацией выполняются анализ и детальный план. Код пишется только после явного согласования плана с пользователем.
3. **Обучение.** В объяснениях упор на важные и сложные аспекты. Базовые конструкции языка не перегружают коммуникацию.

4. **Простота** Использовать всегда только самые простые подходы к проектированию, но с учетом лучших практик. Не создавать сложно контролируемые абстракции. Функции пишите короткие, которые выполняет небольшую одну задачу.

5. **Коментарии** В коде оставляете лаконичные коментарии к функциям какие аргументы принимает какой результат функция возвращает, и краткое описание механики самой функции. Кроме функция оставляйте комментарии через '#' в самом коде в строках где требяется явное обоснавание что происходит

6. **Логирование** Весь код должын быть покрыт логированием основных реализаций. Логи должны показывать что функция удачно запустилась, выполнили свою работу и вернула результат с. Логирование лаконичное должно быть, уровни логов сами определяйте где и какие должны быть. В логах дату не забывайте ставить.

## Файлы правды (единые источники истины)

**Технические карты проекта:**
- **ARCHITECTURE.md** — карта приложения (структура кода, API, модели, сервисы, репозитории)
- **DATABASE.md** — схема БД (таблицы, связи, поля, индексы)
- **AGENTS.md** (этот файл) — правила разработки и процесс работы

**ВАЖНО:** Эти файлы всегда актуальны и синхронизированы с кодом.

## Старт работы

1. Читать **AGENTS.md** (этот файл) — правила и процесс работы
2. Изучать **ARCHITECTURE.md** — понять структуру приложения
3. Изучать **DATABASE.md** — понять схему данных
4. Читать **README.md** — команды запуска и быстрый старт
5. Только затем переходить к конкретным файлам кода

## Процесс работы

1. **Анализ.** Тщательно изучать задачу, задавать уточняющие вопросы, отмечать потенциальные риски и конфликты.
2. **Планирование (Plan).** Готовить детальный план с обоснованием архитектурных решений. Предлагать основной вариант и две альтернативы. Получать явное подтверждение плана.
3. **Реализация (Act).** Строго следовать согласованному плану, создавая понятный и минималистичный код. Любые улучшения или рефакторинг обсуждать заранее.
4. **Обновление файлов правды.** ПЕРЕД коммитом обновить ARCHITECTURE.md и DATABASE.md, если изменения затрагивают:
   - Новые файлы/модули/функции/классы
   - Новые API эндпоинты
   - Изменения в БД (таблицы, поля, связи)
   - Изменения в конфигурации или структуре проекта
5. **Самопроверка (Review).** Перед передачей результата перечитывать изменения, проверять ключевые сценарии и фиксировать важные наблюдения.

- При ревью начинать с критики и проблем, затем отмечать положительные моменты и завершать конкретными рекомендациями по улучшению.

## Практики разработки

- Соблюдать PEP 8 и полную аннотацию типов.
- Функции делать короткими и единственной ответственности.
- Pydantic применять для моделей и валидации данных.
- Логирование выстраивать по уровням INFO, DEBUG, ERROR.
- Обеспечивать базовую валидацию критичных входных данных.

## Архитектура проекта

- Единственный конфигурационный файл `config.py`.
- Единственная точка входа `main.py`.
- Секреты хранить в `.env`.
- Чёткая структура директорий; каждый модуль содержит блок `if __name__ == "__main__":` для автономной отладки.
- Тесты и README создаются только по явному запросу пользователя.

## Работа в Jupyter Notebook (если пользователь упоминает что начинает вести работу в Jupyter)

- Код исполняется по ячейкам: импорты — в первой ячейке, определения функций и классов доступны после объявления.
- Исключать дублирование кода между ячейками, учитывать сохранение состояния.

## Управление зависимостями и инструменты

- Использовать `pip` и файл `requirements.txt` без явного указания версий.
- Предпочитать современные библиотеки: FastAPI, Pydantic, pathlib, pytest.
- При работе с внешними API придерживаться практик уровня OpenAI: простота и скорость решений.

## Структура Python-файлов

- Каждый `.py` файл начинается со строки с относительным путём (`# src/package/module.py`), за которой следует блок `agent_meta` с контрактом, владельцем и ключевыми интерфейсами.
- Блок `agent_meta` — это обязательная метаинформация, которая позволяет быстро понять назначение файла без чтения реализации. Перед изучением кода сначала читать этот блок.
- При изменении публичного контракта или назначения модуля обновлять данные в `agent_meta`, чтобы сохранить актуальность подсказок.
- Пример блока:

```python
# src/services/auth.py
# --- agent_meta ---
# role: auth-service
# contract: предоставляет /login и /refresh
# last_reviewed: 2025-01-10
# interfaces:
#   - login(username: str, password: str) -> TokenPair
#   - refresh(token: str) -> TokenPair
# --- /agent_meta ---
```
